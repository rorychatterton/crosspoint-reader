# Test tailnet bootstrap in ESP32-C3 QEMU

This integration test runs the real MicroLink control-plane, relay and WireGuard data-path code in Espressif's ESP32-C3 QEMU. A local Go server uses Tailscale's `controlhttpserver` package for the ts2021 Noise handshake, serves deterministic registration and peer-map responses over HTTP/2, and runs a real DERP relay (`tailscale.com/derp/derpserver`) behind TLS with a throwaway self-signed certificate. The firmware is built with `ML_DERP_HOST`/`ML_DERP_PORT` pointing at that relay, so no internet access is needed.

The fixture's tailnet peers are real WireGuard endpoints. Each of `api-gateway` (100.64.0.42), `lab-gw` (100.64.0.77, also owning the routed 100.70.0.42) and `lab-dns` (100.64.0.53) is a `wireguard-go` device (`github.com/tailscale/wireguard-go`) with a gVisor userspace IP stack (`control_fixture/netstack.go`) and a `conn.Bind` whose only transport is the fixture's own DERP relay (`control_fixture/wgpeer.go`): the bind connects a `derphttp` client with the peer's node key, hands relayed WireGuard frames to the device with the sender's node key as the endpoint, and sends replies back through the relay. Disco packets (`TS💬` magic) and DERP control frames are ignored. The map advertises the peers' real node keys, and every map fetch hands the reader's node key (`NodeKey` in the request) to each peer as its WireGuard peer with `100.64.0.1/32` allowed. Each peer serves `GET /` on port 80 from its stack (body `tailnet-ok <peer> <request-host>`) and `GET /bulk?bytes=N` (N bytes of a deterministic xorshift32 stream seeded with `0x2545f491`, emitted as little-endian words, with an exact `Content-Length`; the fixture logs the body's MD5 as `WG_FIXTURE bulk peer=... bytes=N md5=...`), and `lab-dns` answers UDP DNS on port 53: an A record `100.70.0.42` for `calibre.lab.qemu.test`, NXDOMAIN otherwise. Every request is logged with a `WG_FIXTURE` prefix in `control.log`. `go test` in `control_fixture` covers the bind (two in-process binds exchanging a packet through a relay), two in-process `wireguard-go` peers carrying HTTP over the relay, the DNS responder, the map wiring, the bulk stream, and a 256 KB bulk transfer between two in-process peers over an impaired relay.

The peers' DERP bind can impair the relay (`control_fixture/impair.go`). `FIXTURE_DROP_PCT`, `FIXTURE_DUP_PCT` and `FIXTURE_REORDER_PCT` (or the `-drop-pct`, `-dup-pct`, `-reorder-pct` flags) are per-frame percentages: drop and duplicate apply to WireGuard frames in both directions; reorder holds an outbound frame back until the next one has been sent (or 30 ms, whichever comes first). The generator is seeded (`FIXTURE_IMPAIR_SEED`, default 1) so a run is reproducible. The fixture logs `WG_FIXTURE impairment drop_pct=... dup_pct=... reorder_pct=... seed=...` at startup and `WG_FIXTURE impairment_stats peer=... dropped=... duplicated=... reordered=...` after each bulk transfer. Unset, the clean path has no impairment hook in it.

The QEMU `sdkconfig.defaults` mirrors the `[firmware_tuned_c3]` mbedTLS settings from the main `platformio.ini` (asymmetric 16 KB/4 KB records, dynamic buffers). Keep the two in sync: DERP's TLS allocation is the first heap-sensitive step after the peer map, and the harness is only representative while they match.

Run the test from the repository root:

```sh
test/tailnet_qemu/run_integration.sh
```

Pass one or more environment names to run selected scenarios:

```sh
test/tailnet_qemu/run_integration.sh qemu_v6_missing qemu_v6_malformed
```

After every QEMU run the script fails the scenario if the guest log contains `assert failed`, `Guru Meditation`, `abort()` or `Backtrace`. lwIP is built with `CONFIG_LWIP_CHECK_THREAD_SAFETY=y`, so a `netif_*`, `udp_*` or `sys_timeout` call made without the TCP/IP core lock asserts here the same way it does on the X3.

The script builds and checks thirteen firmware variants:

- `qemu_eager` recreates the pre-v6 startup order. It constrains the heap to the device's post-task range and requires `TCP connect failed: 113`.
- `qemu_v6` receives 4 KB from a 401-peer map. The target is in that prefix, and the fixture withholds the rest for 20 seconds. The client must select the target and close the control socket without waiting for the full map. It must then complete the DERP TLS handshake and HTTP upgrade against the local relay, reach the coordinator's CONNECTED state (`QEMU_PASS stage=derp-connected`), and complete a DERP-relayed WireGuard handshake with the fixture's `api-gateway` peer when `microlink_wait_peer_ready()` is called (`HANDSHAKE COMPLETE`, `QEMU_INFO stage=peer-handshake result=ESP_OK`). The guest then opens a plain lwIP BSD socket to 100.64.0.42:80 and sends `GET / HTTP/1.0` with `Host: calibre.lab.qemu.test`; the reply must carry `tailnet-ok api-gateway calibre.lab.qemu.test` (`QEMU_PASS stage=tunnel-http`), and the fixture must have logged the request (`WG_FIXTURE http peer=api-gateway`). That is TCP through the WireGuard netif in both directions: lwIP routing onto the netif, encryption, DERP relay, decryption on the wg_mgr task and delivery to the TCP/IP thread.
- `qemu_v6_full` puts the target at the end of the 122 KB map. The client must process the complete response, then pass the same relay stages as `qemu_v6`.
- `qemu_v6_routed` puts the target address (100.70.0.42) only in the `AllowedIPs` of `lab-gw` (100.64.0.77), the shape of a subnet router or Tailscale VIP service, and hands the client a hostname that is not a MagicDNS name. The client must select `lab-gw` at the end of the 122 KB map, install the route on the WireGuard peer (`Route 100.70.0.42/32 via peer lab-gw`), pass the relay stages, complete the handshake with `lab-gw` for the routed address (`result=ESP_OK`), and fetch `GET /` from 100.70.0.42 through it (`QEMU_PASS stage=tunnel-http ip=100.70.0.42`, body `tailnet-ok lab-gw ...`).
- `qemu_v6_resolver` is the routed map plus a `lab-dns` node (100.64.0.53) listed first, and asks for it as the secondary peer (`secondary_peer_ip`), the shape of a split-DNS session where the reader needs both the resolver and the target. Both peers must arrive from the one map fetch, the route must be installed, and both handshakes must complete (`QEMU_PASS stage=secondary-peer arrived=1 handshake=ESP_OK peers=2`). The guest then points lwIP's resolver at 100.64.0.53 (`dns_setserver` under the core lock, cache cleared), resolves `calibre.lab.qemu.test` with `getaddrinfo` (UDP through the tunnel to `lab-dns`, `QEMU_PASS stage=tunnel-dns ip=100.70.0.42`, `WG_FIXTURE dns peer=lab-dns q=calibre.lab.qemu.test`) and fetches `GET /` from the resolved address through `lab-gw`.
- `qemu_v6_resolver_late` is the same map with `lab-dns` listed after `lab-gw`, as the last peer. The filter must keep streaming past the target until the secondary is found: the map bytes it consumed must cover the fixture's whole response, and both peers must still arrive, handshake, resolve and fetch as in `qemu_v6_resolver`.
- `qemu_v6_resolver_absent` asks for the secondary peer against a map that has no `lab-dns`. The client must log `Resolver peer 100.64.0.53 absent from map; continuing with the target only`, reach CONNECTED with the target as its only peer (`QEMU_PASS stage=resolver-absent target=1 peers=1`), select no resolver, and still fetch 100.70.0.42 through `lab-gw`.
- `qemu_v6_restart` reproduces the reader's two-phase split-DNS session. Phase 1 targets `lab-dns` by IP with no name and no secondary, waits for CONNECTED, then calls `microlink_stop()` and `microlink_destroy()` (`QEMU_INFO stage=session-stopped`). Phase 2 calls `microlink_init()`/`microlink_start()` again for 100.70.0.42 with the resolver as secondary and must reach CONNECTED a second time (`QEMU_PASS stage=restart`), then handshake with both peers (`QEMU_INFO stage=peer-handshake result=ESP_OK resolver=ESP_OK`), resolve through `lab-dns` and fetch through `lab-gw`. The script requires two CONNECTED transitions, two `DERP_FIXTURE upgrade` lines, the `lab-gw` route, the DNS and HTTP passes, and free heap after the second bring-up within 4096 bytes of the first.
- `qemu_v6_bulk` passes the `qemu_v6` data-plane stages against `api-gateway`, then fetches `GET /bulk?bytes=1048576` over a plain lwIP socket through the tunnel. The guest streams the body in 1 KB `recv` chunks, compares every byte with its own copy of the xorshift32 generator, MD5s it with the ROM `esp_rom_md5_*` routines, and logs `QEMU_PASS stage=tunnel-bulk ip=100.64.0.42 bytes=1048576 ms=<elapsed> kbps=<rate> md5=<hex>` (or `QEMU_FAIL stage=tunnel-bulk step=... received=... mismatches=... first_mismatch=...`). The script requires the pass line, the fixture's `WG_FIXTURE bulk peer=api-gateway bytes=1048576` line, the same MD5 on both sides, and free heap after the transfer (sampled after a one-second settle on each side) within 4096 bytes of free heap before it. No 1 MiB buffer exists on either side; the guest's verification state is the generator, the MD5 context and one 1 KB chunk.
- `qemu_v6_bulk_lossy` is the same firmware and checks, run against a fixture restarted with `FIXTURE_DROP_PCT=2 FIXTURE_DUP_PCT=1 FIXTURE_REORDER_PCT=1`. The transfer must still be byte-exact and MD5-identical, and the fixture's `impairment_stats` line must show non-zero dropped, duplicated and reordered counts, so a pass cannot come from an impairment that never engaged. The script restarts the clean fixture afterwards for any scenario that follows. Log lines from the fixture are appended to `control.log` across restarts.
- `qemu_v6_stalled` withholds the map before the target. `microlink_get_last_error()` must report the received Noise record count and map byte count while the coordinator waits.
- `qemu_v6_missing` sends a complete map without the requested peer. The client must report `target peer absent`.
- `qemu_v6_malformed` sends invalid JSON in a valid HTTP/2 response. The client must report `Malformed HTTP/2 or JSON`.

The script downloads the Espressif QEMU 9.2.2 release to `.cache` and verifies its SHA-256 checksum. It also builds the Go fixture and the selected firmware variants.

Guest connections to 10.0.2.100:80 and :18443 reach the fixture through QEMU's `guestfwd=...-cmd:` form, which runs `control-fixture -pipe 127.0.0.1:<port>` once per guest connection. The chardev form (`guestfwd=...-tcp:host:port`) opens one host connection when QEMU starts and multiplexes every guest connection onto it, so a second session's control or DERP connection would land inside the first session's stream and hang; `qemu_v6_restart` depends on this.

This test covers the ESP32-C3 allocator, FreeRTOS task stacks, lwIP sockets, MicroLink Noise, HTTP/2, registration, targeted map parsing, DERP TLS and protocol handshake, a completed DERP-relayed WireGuard handshake (link-up, session keys), TCP (HTTP) and UDP (DNS) through the WireGuard netif in both directions, including the routed-address and split-DNS shapes, and a 1 MiB TCP download through the tunnel on a clean and on a lossy relay. Every scenario that reaches the data plane ends with `STACK_HWM min-free/size bytes: coord=... derp_tx=... net_io=... wg_mgr=...` from `microlink_log_stack_watermarks()`; the harness uses mbedTLS for DERP TLS and OpenETH instead of Wi-Fi, so treat the numbers as indicative of the device's wolfSSL marks, but a stack overflow or heap drift here is a real regression. It does not emulate the X3 display, the SD card, the Wi-Fi radio, STUN/disco direct paths, TLS through the tunnel, the real Tailscale control plane, or the reader application itself. Those need a real `tailscaled` peer or hardware (see the workspace `TAILNET_INTEGRATION_PLAN.md`).

Note for device debugging: the targeted map path never parses the control plane's DERPMap, so on hardware the reader always relays through the compile-time `ML_DERP_HOST` (`derp9e.tailscale.com`, Dallas) regardless of its assigned home region.
